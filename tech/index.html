技術ポートフォリオ

一次創作サークル「百花繚乱研究所」のサークル主 ラジアン(柏木主税) です。 VS Code ＋ AIエージェント（Claude / GitHub Copilot / Codex）で、 自分の運用課題を解決するツール・Botを、設計から本番運用まで一人で回しています。

創作活動そのものについては サイトトップ をご覧ください。 このページは開発面の実績に絞ってまとめています。

開発者としての現在地

AIエージェントを「使う」だけでなく「働かせる」構成を設計している

AGENTS.md を Single Source of Truth とし、 CLAUDE.md / copilot-instructions.md を薄い入口として派生させる構成を、 複数のリポジトリで実運用しています。 タロットBot「錦野舞」では、Claude / GitHub Copilot / Codex / Misskey Bot という 4つの入口がすべて同じ正本を実行時に読む構成まで踏み込みました。設定を複製していないため、 正本を書き換えるだけで4つの挙動が同時に変わります。 MCP（Model Context Protocol）を使って、AIから外部ツールやローカルファイルを操作する連携も実装済みです。

AI生成コードを検証する仕組みを持っている

主力の APHRNTs_100 は、実装 約5,200行に対してテストが 約4,200行（vitest 46ファイル）あります。 AIに書かせたコードをそのまま通さず、テストで検証してからマージする運用を取っています。

要件定義から本番運用・障害対策まで一人で通している

Misskey AI Bot 3本を運用しており、うち2本はGCP上で常時稼働させています。 master マージ後の自動デプロイと、3層ウォッチドッグ（プロセス / VM内 / VM外部）による自動復旧まで構築しました。 1本目で作った運用基盤は、2本目へそのまま横展開しています。

主力プロジェクト

APHRNTs_100 本番稼働中

生活管理・セルフケア支援のMisskey AI Bot（TypeScript / Node.js）

課題
体調や生活の記録を自分で続けたかったが、既存のアプリでは記録の形式を自分で決められなかった。
技術
TypeScript / Node.js / SQLite / vitest / GCE（systemd常駐）/ Cloud Run functions / Cloud Scheduler
規模
実装 約5,200行（59ファイル）、テスト 約4,200行（46ファイル）、運用スクリプト 約1,100行
設計判断
Anthropic / OpenAI / Gemini を共通インタフェースで切り替えるマルチLLM抽象化。 Markdownログ ⇄ SQLite の双方向同期を、全文置換ではなくマーカー区間のみ置換する方式で実装し、 手書きの記録を壊さないことを最優先の制約に置きました。 記録の実体はgit管理外とし、公開しているのは記録の形式と仕組みだけです。

NumberTales-MisskeyAIBot 本番稼働中

創作キャラクターのMisskey AI Bot（TypeScript / Node.js）

課題
創作キャラクターを継続的に発信したかったが、手動での投稿は続かなかった。
技術
TypeScript / Node.js / SQLite / GCP VM / PM2 / GitHub Actions
設計判断
キャラクター設定の正典は公開データベース側に置き、Botからはサブモジュールとして参照する構成にして、 設定の二重管理を避けました。 システムプロンプトは「キャラクターの識別・口調」と「Botとしての実行制約」を分けた二層構成で自動生成しています。 3層ウォッチドッグ（PM2 / VM内systemd timer / Cloud Scheduler + Cloud Run functions）で、 人手を介さず復旧する構成を取りました。

Tarot-byFateLineDealer 運用中

タロット占いBot「錦野舞」。1つの正本を4つの実行環境が共有する構成（Python）

課題
同じキャラクター・同じ手順を、チャット（Claude / Copilot / Codex）でもBotでも使いたかった。 環境ごとに設定を書き写すと、必ずどこかが古くなる。
技術
Python / Claude API / Misskey API / Pillow（画像合成）
設計判断
キャラクター設定と運用ルールの正本を2ファイルに限定し、 4つの入口すべてが実行時にその正本を読む構成にしました。Bot側へ設定をコピーしていないため、 正本を書き換えれば4つの挙動が同時に変わります。 カードの抽選は乱数スクリプトに分離して公正性を担保し、 投稿は既定で dry-run、実投稿には明示的なフラグを要求する設計にしています。

100BeautiesLab_CreationsDB

静的ホスティング上に擬似REST APIを実装した、創作キャラクターの公開データベース

課題
創作設定が膨大になり、手元のファイルでは管理できなくなった。機械可読な形で公開したかった。
技術
JavaScript (ES6+) / Service Worker / SASS / GitHub Pages
設計判断
サーバーを借りずに済ませるため、Service Workerでリクエストを傍受してJSONから応答を組み立てる擬似APIを実装。 用途の異なる3スコープ（標準 / UI向けエンリッチメント付 / ミラー）を出し分けています。 型定義（db_type.json）をデータと同じリポジトリに置き、定義自体もAPIから引けるようにしました。 DB間・作品間を横断する参照解決エンジンも自前で実装しています。
